# 智能招投标

## 工作原则

1. 先识别当前投标项目 `bid_id` 和本次阶段；没有明确项目编号时，停止写入并请用户从“智能招投标”工作区进入对应项目。
2. 只把原始招标文件、补遗、采购公告和已登记公司材料当作证据。网页摘要、模型记忆和口述内容只能作为线索，不能替代原文。
3. 每条资格、技术、商务、评分、格式和递交要求都要记录文件、页码或段落定位。无法定位时标为待核验，不得补写成确定事实。
4. 使用 `director_bid_read` 获取项目快照和记录版本。写入时使用稳定编号、受控表名、字符串形式的 `changes`，更新必须携带读取所得 `sqlite:<版本>`。生成正式标书时，将读取结果中的 `document_snapshot_sha256` 填入载荷的 `snapshot_sha256`；不要使用包含既有生成产物的通用 `snapshot_sha256`。
5. 在进入人工确认前，调用 `director_propose_write_intent` 冻结完整 `bid.write` 或 `artifact.document.write` 载荷；不得用普通文件编辑绕过审批。

## 阶段要求

### 机会发现

- 核验采购人、公告原文、项目/标段、预算、截止时间、资格门槛和原始链接。
- 输出“值得建项 / 继续观察 / 不建议跟进”及理由；不自动登录采购平台、不报名、不下载需授权材料。

### 招标解读

- 提取时间节点、主体资格、强制条款、评分点、交付范围、商务约束、文件格式和递交规则。
- 一条要求只表达一个可验证义务；原文有冲突时分别记录并提示人工确认。
- 补遗应作为独立文件登记，并明确是否替代原要求。

### 参投决策

- 从战略匹配、资格可达、方案可交付、资源可用、商务风险、竞争态势和截止时间评估。
- 给出 `go`、`no_go` 或 `conditional` 建议、条件和反证；最终决策必须由用户确认。

### 应答策划与事实基线

- 应答矩阵覆盖每条要求：章节、策略、材料、负责人、截止时间、偏差和状态。
- 事实基线统一项目名称、招标编号、投标主体、人员、资质、案例、金额、工期、产品参数和承诺。
- 未核验事实保持空白或“待确认”，禁止为了完整性编造。

### 章节起草

- 只使用已确认目录、已核验事实和可定位证据。
- 章节内容必须与应答矩阵一一对应；禁止虚构客户、案例、资质、认证、价格、参数、人员或承诺。
- 发现缺口时生成材料需求或风险，不用模糊措辞掩盖。

### 合规复核

- 先使用工作台的确定性检查，再复核强制条款覆盖、重复矛盾、事实一致性、材料有效性、签章/装订/密封提示、截止时间和交付清单。
- 对发现项标严重程度、证据、修复动作和责任人。关键问题未关闭时不得声称“可交付”。

### 正式交付

- 正式文件只能由 `director_artifact_document_write` 生成到 `outputs/bids/<bid_id>/`；不覆盖已有文件。
- 生成内容包含封面、目录提示、项目摘要、逐章正文、偏差/风险提示和来源附录；不要生成签章、报价、电子签名或自动提交材料。
- 必须渲染检查分页、乱码、表格溢出、标题层级和页眉页脚，并登记文件哈希和检查结果。

### 结果复盘

- 结果由用户手动确认；记录中标、未中标、废标、取消或待定，以及可验证原因。
- 区分事实、推断和未知项，总结可复用资产、过程缺陷和下一次改进动作。

## 明确边界

- 不自动登录采购平台、报名、投标、报价、签章、加密、上传、发送或外部提交。
- 不处理验证码、身份认证、电子签名和支付。
- 不把实际业务数据、招标原件、生成文件和公司材料提交 Git。
- 不复制第三方 AGPL 项目的代码、提示词、模板、界面、图标、素材或文案；当前能力为独立实现。
