## 1. 交付目标

阶段 A 的完成标准不是“数据库能打开”，而是销售总监能够完成以下闭环：

```text
选择客户 → 查看完整上下文 → 识别有依据的信号 →
确认/编辑下一步 → 经 Approval 事务写入 →
从同一客户上下文启动复盘、政府合作或汇报 → 可恢复、可追溯
```

整个阶段分为六个顺序工作包。A0 是技术门禁；A1–A2 建立数据底座；A3–A4 交付用户价值；A5 执行迁移、跨平台和发布验证。不得绕过 A0 直接把业务数据迁入新库。

## 3. A0：SQLite 驱动与故障门禁

### 3.1 任务

- 新增最小 `LocalBusinessStore` 原型，只实现建库、单表增删改查、批量事务和回执。
- 固定候选 Node 24.x 补丁版本，记录 Node、SQLite、Python 和操作系统版本。
- Windows x64、macOS arm64、macOS x64 执行相同测试向量。
- 注入以下故障：
  - `BEGIN` 后、业务更新前终止进程。
  - 业务更新后、回执写入前终止进程。
  - `COMMIT` 返回后、任务状态更新前终止进程。
  - 两个任务更新同一版本。
  - 长读与短写并发、数据库忙、磁盘空间不足、只读目录。
- 用 Python `sqlite3` 只读检查同一数据库和备份。

### 3.2 决策规则

- 全部通过：确认固定 Node 24.x + `node:sqlite`。
- API、打包或恢复存在阻断：暂停 A1，评估 `better-sqlite3` 的四平台预构建、签名和升级成本。
- 不允许在运行时根据“哪个驱动可用”静默选择实现；安装包只使用一种经过验证的驱动。

### 3.3 验收

- 同一 intent 重试 100 次仍只产生一次业务变更。
- 并发版本冲突不会覆盖新值。
- 强制终止后每个意图都能确定为 committed 或 not committed。
- 5 秒锁预算到期后返回可恢复错误，界面不无限等待。
- 三个平台测试结果结构一致并生成机器可读报告。

## 4. A1：存储内核、schema 与迁移

### 4.1 建议代码边界

```text
agent_platform/
├─ migrations/
│  ├─ 001_sales_core.sql
│  └─ manifest.json
└─ sales_store.py
pi/extensions/
├─ business-store.ts
├─ local-business-store.ts        # A0 驱动门禁原型
└─ data-adapters.ts

├─ sales-mutation.schema.json

├─ fixtures/sales-migration/
└─ test_sales_store_migration.py
pi/tests/
└─ local-business-store.test.ts
```

文件名是建议边界；实现时应遵循仓库现有命名和构建规则，避免把所有 SQL、迁移和适配逻辑继续堆入 `data-adapters.ts`。

### 4.2 任务

- 实现 schema v1、外键、索引、版本表和连接配置。
- 实现参数化查询、短事务、`expected_version` 和统一错误码。
- 把 `write_receipts` 与业务 mutation 放在同一事务。
- 实现 CSV 预检、staging 导入、行级隔离、对账和迁移摘要。
- 实现备份、完整性检查、存储指针原子切换和恢复。
- 实现显式 CSV 导出；导出内容防公式注入并附清单哈希。
- 更新 `.gitignore`，覆盖数据库、WAL、SHM、备份、导入报告和业务导出。

### 4.3 迁移测试数据集

至少包含：

- 正常的 4 张销售表和来源登记表。
- 空文件、仅表头、UTF-8 BOM、中文、逗号、换行和长文本。
- 重复主键、缺失客户、非法时间、未知状态和损坏 CSV。
- 同名客户但不同 ID、同一客户多机会、孤立互动。
- 不存在或越界的文件路径、PDF 无页码、URL 含敏感参数。
- CSV 公式注入值，如 `=SUM(...)`、`+cmd`、`@...`。
- 16 MiB 边界附近的输入和超过限制的输入。

### 4.4 验收

- 每个输入行都有明确导入结果，无静默丢弃。
- 有效记录主键、数量和关键字段对账一致。
- 无效行保留原始行 JSON 和错误代码，但不进入业务表。
- 用户批准切换前，运行时仍读取旧存储。
- 切换失败能恢复指针和备份；原 CSV 从未被覆盖或删除。
- 迁移后导出 CSV 再导入新空库，核心字段和关联关系等价。

- 当前销售复盘 DAG 不因存储替换改变用户可见步骤和 Approval 语义。

- 旧 CSV 模式只用于迁移前与回滚窗口；切换后不做双写。

### 5.3 验收

- 当前所有运行时和 Python 测试先在旧存储通过，再在 SQLite 存储通过。
- 相同 fixture 的关键查询得到语义等价结果。
- 已批准但未提交的旧任务在升级后需要重新确认，或被明确标记不兼容；不得静默提交到新存储。
- `sales.write` 的冻结 payload 改变时，旧批准立即失效。

### 6.1 页面增量

#### 工作台

- 新增“今日关注”：逾期行动、承诺临期、长期无互动、资源申请临期和待确认变化。
- 每张卡片显示客户、触发原因、截止时间和首要操作；点击直达客户 360 对应区域。
- 快速输入自动带入当前客户，但输入框上方始终显示且可清空上下文。

#### 客户列表

- 支持关键词、负责人、地区、行业、阶段、健康度和更新时间筛选。
- 显示最近有效互动、开放行动数、风险数和数据新鲜度。
- 疑似重复客户只显示提示，不在列表刷新时自动合并。

#### 客户 360

- 概览：客户事实、机会、主要风险、首要行动和缺失信息。
- 时间线：互动、承诺、任务、批准写入和产出。
- 关键人：角色、影响、决策关系、最近互动和证据状态。
- 信号与建议：触发依据、状态、接受、编辑或忽略。
- 资源与资产：申请、审批、方案和使用反馈。
- 证据：来源、页码/段落、核验状态、最后访问时间。

### 6.2 交互状态

每个页面必须覆盖加载、空数据、部分数据、冲突、数据库忙、来源失效、权限拒绝和恢复状态。轮询刷新不得：

- 抢走输入焦点。
- 将滚动位置复位到顶部。
- 展开用户已折叠的卡片。
- 覆盖尚未提交的本地编辑。

### 6.3 验收

- 从首页关注卡到相应客户证据不超过 2 次点击。
- 从客户页启动复盘、政府合作、资源协调或 PPT 不超过 3 次主动操作。
- 连续切换 20 个客户不存在上下文串用。
- 10,000 个客户、100,000 条互动的基准数据下，常用查询 P95 ≤ 2 秒。
- 键盘可完成客户搜索、切换标签、打开建议和关闭抽屉。

## 7. A4：信号、行动建议与 Play 层

### 7.1 确定性信号规则

| 规则 | 输入 | 触发条件 | 自动解除条件 |
|---|---|---|---|
| 逾期行动 | 开放 action | `due_at < now` | 完成、取消或修改截止时间 |
| 长期无互动 | 客户最近有效 activity | 超过用户配置阈值 | 新增有效互动 |
| 承诺临期 | open commitment | 距截止时间小于阈值 | 履行、取消或延期 |
| 关键字段缺失 | 客户/机会字段 | 当前 Play 需要但为空 | 字段经批准补齐 |
| 资源申请临期 | open request | 距 deadline 小于阈值 | 完成、拒绝或延期 |

规则版本、阈值、时区和触发记录全部进入 fingerprint。模型不负责判断规则是否触发。

### 7.2 建议生成

- 规则先确定“发生了什么”；模型只在允许范围内解释影响和提出可选行动。
- 每条建议包含：事实依据、分析、未知信息、建议行动、负责人候选、截止时间候选和来源。
- 未知信息足以改变方向时，先向用户提问，不生成确定行动。
- 接受/编辑后接受会形成待批准 `sales.write`；忽略只记录反馈，不改变业务状态。

### 7.3 首版 Play

1. 客户进展复盘。
2. 政府合作方案。
3. 行业专题研究。
4. 销售资源协调。
5. 周报/PPT 汇报。

Play 不是新的固定 DAG 复制。它是目标、输入 schema、允许数据范围、工具权限、输出类型和审批点的版本化组合；底层可复用现有工作流。

### 7.4 验收

- 同一数据版本重复运行规则不会产生重复活动信号。
- 信号展示的每个字段都能定位到触发记录。
- 建议中的事实均有证据；分析、假设和未知标签在页面与导出中一致。
- 用户编辑建议后，批准绑定编辑后的 payload，旧 hash 不可复用。
- 五个 Play 均能从自然语言和客户页启动，已有信息不重复询问。
- 修改 Play 定义后，历史运行仍能定位旧版本和定义哈希。

## 8. A5：切换、双平台和发布

### 8.1 试运行顺序

1. 复制一份真实业务数据到隔离测试目录，做只读预检。
2. 用户审阅数据质量报告，修复会影响客户身份和关联的阻断项。
3. 在 staging 数据库完成导入、对账和客户页面 UAT。
4. 备份正式数据，冻结短暂写入窗口。
5. 用户批准切换；原子更新存储指针。
6. 完成冒烟、两次重启和一次恢复演练。
7. 观察期内保留 CSV 只读快照；所有新数据仅写 SQLite。

### 8.2 安装与升级

- Windows 安装位置仍可为 `E:\PersonalWorkSpace\Agent4Market`，但业务数据目录与程序目录分离。
- macOS 同时验证 Apple Silicon 与 Intel 架构；应用升级不覆盖用户数据库。
- 安装器在升级前检查支持的 schema 版本和备份空间。
- 卸载默认保留业务数据；彻底删除数据必须由用户单独确认。

### 8.3 发布门禁

- A0–A4 退出条件全部满足。
- Windows/macOS 构建、安装、启动、迁移、重启和卸载测试通过。
- 所有现有服务、政府合作、知识库、报销、项目空间、周报和 PPT 回归通过。
- 无未关闭 P0/P1；涉及数据损坏、越权写入或错误 Approval 的 P2 也必须关闭。
- 真实数据 UAT 得到销售总监明确确认。

## 13. 风险与应对

| 风险 | 影响 | 预防/缓解 | 决策点 |
|---|---|---|---|
| 后续 Node 升级导致 SQLite 门禁回归 | 阻断发布 | 固定 24.19.0；升级时重跑三平台故障门禁 | 每次运行时升级 |

## 14. 第一批可执行开发任务

按顺序创建任务，不并行修改同一存储核心：
